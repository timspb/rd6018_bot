### 1. Цель и целевая структура

Главная цель — полная декомпозиция RD6018 и модульная архитектура без изменения принятого поведения, без второго параллельного двигателя и без усложнения ради архитектуры. Сначала исследование существующей реализации и фактического call graph, затем решение ChatGPT, fake-only parity, узкий перенос ответственности, независимая регрессия и обязательная запись в документы.

| № | Функциональный отдел | Основная зона ответственности |
|---:|---|---|
| 1 | Battery / Chemistry | Химия, профили, ограничения, чистые доменные решения |
| 2 | Charge Engine | MAIN, MIX, AGM, EFB, desulfation, Imin, stage transitions |
| 3 | Application | START, STOP, SET, COOLING, MIX, RECOVERY use cases |
| 4 | Safety Authority | Safety decisions, admission, lease, trips, OFF policy |
| 5 | Physical Execution | Единственный существующий ExecutionPort и физические адаптеры |
| 6 | Telemetry / Evidence | Измерения, freshness, provenance, normalized evidence |
| 7 | Sessions / Persistence | AUTO, Manual, operator state, atomic persistence |
| 8 | Recovery / Ownership | Startup, restore, adoption, HANDS_OFF / PB_MANAGED |
| 9 | UI | Telegram, Dashboard, HMI, Recipe Studio, presentation |
| 10 | Integrations | HA, ESP Native, Wake, AI/context, notifications |
| 11 | Composition / Deploy | Composition root, configuration, install/update/rollback/DR |

Для каждого отдела обязательны: один утверждённый функциональный owner; один владелец каждого состояния и решения; явные интерфейсы/DTO/ports; карта входов, выходов, consumers и side effects; независимые тесты; OWNERSHIP.md; проверяемая композиция.
